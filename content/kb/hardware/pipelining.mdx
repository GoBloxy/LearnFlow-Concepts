# Pipelining

## Introduction
Modern processors execute billions of instructions per second. This phenomenal speed is achieved not only by increasing clock frequencies but also by exploiting instruction-level parallelism. One of the most fundamental techniques for achieving this parallelism is **pipelining** – a design methodology borrowed from assembly lines in manufacturing. Pipelining allows a processor to overlap the execution of multiple instructions, improving overall throughput without necessarily reducing the latency of a single instruction. In this article we explore the principles of instruction pipelining, its benefits, the hazards it introduces, and the techniques used to mitigate those hazards.

## What is Pipelining?
Pipelining is an implementation technique in which multiple instructions are processed simultaneously by breaking the execution path into distinct stages. Each stage completes a part of the instruction, and instructions flow through the stages one after another. While one instruction is being executed, another can be decoded, and yet another can be fetched from memory.

Consider a non‑pipelined processor where the execution of a single instruction requires a time $T$. If the same processor is divided into $k$ stages of equal duration, and each stage takes time $t = T/k$, then ideally a new instruction can be started every $t$ units of time. The result is that the processor can complete one instruction per cycle once the pipeline is full, achieving a theoretical speedup of $k$ over the non‑pipelined execution.

### Latency vs. Throughput
- **Latency** is the time it takes to execute a single instruction from start to finish. Pipelining does not reduce latency; in fact, it may slightly increase it because of pipeline register overhead.
- **Throughput** is the number of instructions completed per unit time. Pipelining dramatically increases throughput because multiple instructions are in flight simultaneously.

## The Classic Five‑Stage Pipeline
A widely studied example is the classic RISC five‑stage instruction pipeline. The execution of an instruction is divided into:

1. **IF – Instruction Fetch**  
   Fetch the instruction from memory using the Program Counter (PC).
2. **ID – Instruction Decode / Register Read**  
   Decode the instruction and read operands from the register file.
3. **EX – Execute / Address Calculation**  
   Perform the arithmetic, logical operation, or calculate the effective memory address.
4. **MEM – Memory Access**  
   Access data memory for load or store instructions.
5. **WB – Write Back**  
   Write the result back to the register file.

Each stage is separated by **pipeline registers** that store the data and control signals needed by the next stage. The clock period is determined by the slowest stage plus the pipeline register propagation delay.

### Ideal Pipeline Performance
Assume we have $n$ instructions to execute on a $k$-stage pipeline. In a non‑pipelined processor, the total execution time would be:

$$
T_{non} = n \cdot k \cdot t
$$

where $t$ is the time per pipeline stage (approximating the clock cycle). In a pipelined processor, after the pipeline is filled, one instruction completes every clock cycle. The total time is:

$$
T_{pipe} = (k + n - 1) \cdot t
$$

The ideal speedup is then:

$$
S = \frac{T_{non}}{T_{pipe}} = \frac{n k}{k + n - 1}
$$

For large $n$, $S \approx k$. In practice, the speedup is lower because of overheads and pipeline stalls.

*Example:* Let $k = 5$, $t = 1$ ns. Executing $n = 10$ instructions:  
Non‑pipelined time: $10 \times 5 \times 1 = 50$ ns.  
Pipelined time: $(5 + 10 - 1) \times 1 = 14$ ns.  
Speedup: $50/14 \approx 3.57$, less than the ideal 5.

## Pipeline Hazards
A hazard is a situation that prevents the next instruction from executing in the immediately following clock cycle. Hazards reduce the actual speedup. They are categorized into three classes:

### 1. Structural Hazards
A structural hazard occurs when two instructions require the same hardware resource simultaneously. For example, if a processor has a single memory port for both instructions and data, the IF and MEM stages cannot proceed in the same clock cycle. This is resolved by duplicating resources (e.g., separate instruction and data caches, the Harvard architecture) or by stalling.

### 2. Data Hazards
Data hazards arise when an instruction depends on the result of a previous instruction that is still in the pipeline. There are three types:

- **RAW (Read After Write)**: Instruction $J$ reads a source register before instruction $I$ writes it.  
- **WAW (Write After Write)**: Instruction $J$ writes a register before instruction $I$ writes it – problematic in out‑of‑order pipelines.  
- **WAR (Write After Read)**: Instruction $J$ writes a destination before instruction $I$ reads it – also relevant for out‑of‑order execution.

In a simple in‑order pipeline, RAW hazards are the most common. Consider:

```
add  r1, r2, r3   ; r1 = r2 + r3
sub  r4, r1, r5   ; r4 = r1 - r5
```

The `sub` instruction needs the value of `r1` that is written by `add`. In the five‑stage pipeline, `add` writes `r1` in the WB stage (5th cycle), but `sub` reads `r1` in the ID stage (2nd cycle of `sub`, which overlaps with `add`’s EX stage). The value is not yet available.

#### Forwarding (Bypassing)
Forwarding resolves many data hazards without stalling. The result computed in the EX/MEM or MEM/WB pipeline register can be fed back directly into the ALU input for the next instruction. In the example above, the ALU result from `add` is available at the end of its EX stage, and can be forwarded to the `sub` EX stage in time, avoiding a stall.

#### Stalling (Pipeline Bubble)
Not all hazards can be forwarded. For instance, a **load‑use hazard** occurs when an instruction immediately after a load uses the loaded data. In a five‑stage pipeline, the load data is available only after the MEM stage. A single stall cycle must be inserted (a pipeline bubble) if forwarding is not sufficient.

### 3. Control Hazards
Control hazards occur when the processor encounters a branch instruction. The next instruction to be fetched is not known until the branch is resolved (at the end of the ID or EX stage). The simplest solution is to **stall** the pipeline until the branch outcome is known, but this causes a performance penalty of several cycles.

#### Branch Prediction
Modern processors use branch prediction to guess the outcome (taken/not taken) and the target address. If the guess is correct, the pipeline continues without stalls. If mispredicted, the speculatively executed instructions must be flushed, wasting cycles. Simple static predictors (e.g., always not taken) yield moderate accuracy. Dynamic predictors, such as two‑bit saturating counters, can achieve accuracies above 90%.

#### Delayed Branches
Some RISC architectures (e.g., MIPS) use a **delayed branch** where the instruction immediately following the branch is always executed (the branch delay slot). The compiler fills this slot with an independent instruction, avoiding a stall.

## Deeper Pipelines and Superpipelining
Modern high‑performance processors often have pipelines with 10–20 or more stages (superpipelining). Deeper pipelines allow higher clock frequencies because each stage does less work, but they also increase the misprediction penalty and the complexity of hazard management. The Pentium 4, for example, featured a 20‑stage NetBurst pipeline.

## Superscalar and Out‑of‑Order Execution
To further increase throughput, processors can issue and execute multiple instructions per clock cycle – a technique known as superscalar execution. Instruction‑level parallelism is exploited by the hardware, which must manage multiple functional units and intricate hazard detection. Out‑of‑order execution allows instructions to execute as soon as their operands are ready, rather than in strict program order, boosting utilization of execution units.

While these techniques go beyond the simple in‑order pipeline, they build directly on the pipelining concept by adding more sophisticated control logic and buffering.

## Summary
Pipelining is a cornerstone of high‑performance processor design. By breaking instruction execution into discrete stages and overlapping them, a processor can significantly increase its throughput – approaching an ideal speedup equal to the number of pipeline stages. However, real‑world speedup is limited by pipeline overhead and hazards:

- **Structural hazards** are addressed by resource duplication.
- **Data hazards** are mitigated through forwarding and stalling.
- **Control hazards** require branch prediction or delayed branches to reduce stalls.

The five‑stage pipeline provides a canonical model for understanding these trade‑offs. Extensions such as deeper pipelines, superscalar issue, and out‑of‑order execution continue to push performance boundaries, but at the cost of increased design complexity and power consumption. A thorough grasp of pipelining principles is essential for anyone studying computer architecture and hardware design.
